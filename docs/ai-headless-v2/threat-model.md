# Threat Model — Host Capability 与威胁清单

> **任务：AI2-004（M0 · P0 · S）**
> 验收标准（`design-source/03-IMPLEMENTATION-BACKLOG.md` §M0）：**至少包含命令、文件、审批、日志、跨租户风险**。
> **状态：Proposed（提案）** ｜ **文档时点：2026-10-27**
> **前提声明**：M0 时点本仓库**没有可信 Host / 生产执行端、没有可运行的 V2 UI**；`packages/ai-core` 仅有**实验性**的协议类型与 Mock/Replay Host（`private`，状态以其 [包 README](../../packages/ai-core/README.md) 为准），不构成安全防线。因此本文档列出的所有防线都是**待实现 + 待验证**的目标，不是现状描述；任何"已防护"的表述在本文档中一律不成立。

## 1. 资产（Assets）与最坏后果

| 资产                                            | 最坏后果                                       |
| ----------------------------------------------- | ---------------------------------------------- |
| A1 用户文件系统（工作树、项目仓库）             | 任意读写、覆盖、提交恶意代码                   |
| A2 命令执行（shell、构建、测试、部署）          | 任意代码执行、横向移动、凭证窃取               |
| A3 凭据（API Key、Access Token、环境变量）      | 泄露到浏览器、日志、事件广播、第三方           |
| A4 用户数据（Prompt、附件、工具输出、路径信息） | 跨租户/跨会话泄露、留存超期                    |
| A5 审批事实（Approval 决策）                    | 越权执行高风险操作（假批准、重放、scope 提升） |
| A6 变更集（ChangeSet / Diff）                   | 未经审查的代码落地、冲突静默覆盖               |
| A7 领域状态完整性（Store / seq）                | 伪造事实、回滚终态、隐藏已执行操作             |

## 2. 信任边界（Trust Boundaries）

```text
[不可信]                [边界]                    [可信]
模型输出 / 工具输出  ──► Renderer 消毒 ──►  主应用 DOM
浏览器 UI（Controller）──► Command ───────►  Host（认证/鉴权/策略/目标版本/防重放）
Provider 事件流     ──► 协议校验/去重/排序 ──► Store（事实）
附件 URI / Artifact ──► 可信 Asset Loader ──► 受控渲染
```

核心不变量（来自 `design-source/01-ARCHITECTURE.md` §13.1 五条边界）：

1. **审批是服务端权限决策**：按钮状态、DOM 禁用、前端角色检查**都不构成**安全授权。
2. **模型内容是不可信输入**：Markdown、文件、Shell 输出、工具参数、AI 生成建议都不构成前端执行指令。
3. **审批必须显式显示 scope 与 target**：不能只展示"允许/拒绝"。
4. **危险动作不可省略后端能力与策略检查**（阈值由业务宿主配置）。
5. **日志可审计、敏感数据可脱敏**：用户可见工具明细是脱敏版本。

## 3. Host Capability 矩阵

### 3.1 语义

- Capability 由 **Host 声明**，UI 只读；**未声明 = 不可呈现为可用动作**（`01` §20-4、`02` B4、`03` AI2-301「按钮根据 capability 显示」）。
- Capability 是**产品能力开关**，不是授权凭证：即便声明可用，每次操作仍要过 Host 的认证/鉴权/风险策略/目标版本/防重放检查（`01` §7.3）。
- 载体：`Workspace.capabilities: string[]`（`01` §5.1）、Execution 级能力（`01` §20-4）；列表项为**本文件具体化**，原文只规定机制。

## 4. 威胁清单

### 4.0 风险评级口径

| 等级   | 定义                                                 | 处置要求                            |
| ------ | ---------------------------------------------------- | ----------------------------------- |
| **高** | 可导致代码执行 / 数据外泄 / 权限提升，且默认路径可达 | 必须在本里程碑内建防线 + 自动化测试 |
| **中** | 需特定条件或影响有限，但可被组合利用                 | 必须有防线；测试可后置到对应里程碑  |
| **低** | 主要影响可用性/信息完整性                            | 记录并纳入回归                      |

| -------- | --------------------------------------------------------------------- | ---------------------------- | ------------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

### 4.7 重放与幂等攻击

| ID       | 威胁                                                                      | 攻击者/入口     | 影响               | 风险   | 可验证的防线（层 + 测试）                                                                                                                                                                                                              |
| -------- | ------------------------------------------------------------------------- | --------------- | ------------------ | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **T7-1** | Command 重放（截获后重复提交 `approval.resolve` / `changeset.apply`）     | 网络层/恶意脚本 | 重复副作用、越权   | **高** | 防线：**Host** 强制 `idempotencyKey` 唯一 + 认证绑定；重试必须保留同一 key（`01` §7.3）。测试：换 key 的重放被识别为可疑（非静默成功）                                                                                                 |
| **T7-2** | 事件重放污染状态（同一 `seq` 应用两次）                                   | 重连逻辑缺陷    | 重复消息、计数错乱 | 中     | 防线：`seq <= lastApplied` 丢弃（幂等 reducer）；重复 revision 丢弃（`01` §7.1/§7.2-3）。测试：乱序/重复事件 fixture（AI2-108）                                                                                                        |
| **T7-3** | 伪造未来 `seq` / 跳号导致状态机被跳过（如直接跳到 `completed`）           | 恶意事件源      | 终态伪造、绕过审批 | **高** | 防线：`seq` 只能由服务端签发（`schemaVersion:2` + 服务端权威）；`execution.status.changed` 走合法迁移表校验；`seq > lastApplied+1` 触发缺口恢复而非直接应用（`01` §7.2-3/4）。测试：跳号 fixture + 非法迁移 fixture（AI2-104/106/108） |
| **T7-4** | 用旧 `revision` 的合法事件回滚终态（晚到旧事件逆转 `cancelled`/`failed`） | 乱序到达        | 状态回滚、审计失真 | **高** | 防线：实体 `revision` 单调；终态只接受合法迁移（`01` §6.1、F7）。测试：晚到事件 fixture（`01` §17.1）                                                                                                                                  |
| **T7-5** | 离线重放期间 `changeset.apply` 被重复提交                                 | 重连刷新        | 重复写盘           | 高     | 防线：apply 幂等键 + `baseRevision` 校验；`applying` 状态拒绝二次提交（`01` §7.3、`02` B6）                                                                                                                                            |

## 7. 明确不做 / 无法在本仓库验证的部分

1. **Host 侧的一切强制检查**（认证、鉴权、策略、沙箱、真实写盘）：本仓库不实现 Host，`01` §1.1 也把 LLM/Agent Loop/MCP Runtime/沙箱/Git 执行器/文件存储列为非目标。本文档只能定义"UI 不得代替 Host 做判断"与"协议必须携带什么字段"。
2. **密钥管理**：UI 不保存 API Key，密钥由服务端/本地受信进程持有（`01` §7.4）；本仓库无密钥存储代码，故无相关测试。
3. **速率限制与配额**：属 Host/网关层，本文档只要求 Capability 可表达"不可用"。
4. **供应链与依赖投毒**：不属本里程碑；AI2-509 仅覆盖依赖隔离与打包一致性。
5. **浏览器 0day / 同源 XSS 逃逸**：超出威胁模型范围。

## 8. 残留风险与开放问题

1. **审批决策人身份**：`ApprovalRequest` 目前无 `requestedBy`/`decidedBy` 字段（`01` §5.2），审计"谁批准的"需要扩展字段或由 Host 侧审计日志承担。
2. **离线队列**：若未来允许离线排队 Command，`idempotencyKey` 与 `expectedRevision` 的冲突策略需重新设计（当前明确禁止离线假批准）。
3. **Renderer 第三方插件**：插件由宿主引入即视为可信代码；若要做插件沙箱，需要额外 ADR（当前只要求"渲染不越权"）。
4. **`expectedRevision` 的粒度**：实体级还是聚合级，影响 T3-2/T7-5 的冲突检测精度，需在 AI2-105 明确。
5. **跨 stream 时间线**：`01` §7.2-5 明确不承诺跨 stream 全局排序，混合时间线需显式排序键——这可能被误用为"事件顺序无关"，需在实现文档中强调 `seq` 仅 stream 内权威。
